| D-022 | 2026-07-30 | The availability engine is one gate. `private.require_bookable_appointment_slot` is the single authority for whether a slot can be claimed, and the slot projection (`api_availability_slots`) and quote (`api_quote_appointment`) answer by calling that same gate per candidate inside a subtransaction rather than reimplementing its rules. | Before P2-07 the Express projection and the RPC each carried their own copy of the rules and had already drifted: the projection could offer a slot that the claim then refused. One savepoint per candidate — roughly fifty for a thirteen-hour day — is the price of a structural guarantee that quote and claim cannot disagree. Revisit only if a real shop's slot query becomes slow; the fix would be a cheaper pre-filter in front of the gate, never a second copy of the predicates. | Active |
| D-023 | 2026-07-30 | Chair capacity is enforced as peak concurrency during the candidate's occupied window, serialized by a shop-scoped advisory lock taken before the customer and provider locks. | Counting every appointment that merely overlaps the candidate over-refuses: with two chairs, a 09:30-10:15 and a 10:45-11:30 booking both overlap a 10:00-11:00 candidate but never each other, so the true peak is two, not three. The count can only rise at the candidate's own start or at an existing appointment's start, so probing those instants finds the real maximum. The shop lock is what makes the count stable — without it two transactions each read a pre-insert count and both succeed. Lock order is fixed globally as shop, then customer, then providers in text order, so no cycle is possible. | Active |
| D-024 | 2026-07-30 | A barber becoming active at a shop is granted the shop's currently active services by default, attributed to the employing owner. A service added *later* is deliberately granted to nobody. | Requiring an explicit qualification before anyone is bookable creates a trap in one direction only. Without grant-on-hire a new barber is silently unbookable with no error anywhere until a customer fails to find a slot. The mirror case is not symmetric: auto-granting a *new* service to all existing staff would make P2-05's owner-grant and barber-request flows unreachable, because no barber could ever have a service left to request. Implemented as a trigger on `barber_employment`, not an addition to the acceptance command, so any future path that activates an employment is covered too. `ON CONFLICT DO NOTHING` means a deliberate revocation is never resurrected, including across a re-hire. Reversible: dropping the trigger restores explicit-grant-only. | Active |
| D-025 | 2026-07-30 | Both booking-window columns default to a true no-op: `min_lead_minutes` to 0 and `max_advance_days` to NULL, meaning no horizon. | A migration must not invent a policy the owner never chose. Any finite default horizon would have silently stopped every existing shop from taking bookings beyond it, and the integration fixtures' own far-future appointments proved the failure mode immediately. Zero lead time changes nothing, since the gate already requires a future start. | Active |
| D-026 | 2026-07-30 | When a requested time fails both the barber's shift and the shop's opening hours, the engine reports the shift. | Both refusals are true, so the order is a product choice. "Outside the barber schedule" is the more actionable answer for a customer who has already chosen a provider, and it preserves the pre-P2-07 error contract for requests that were being refused anyway. Shop hours remain decisive whenever they are narrower than the shift, which is the case the regression isolates. | Active |
| D-027 | 2026-07-30 | A shop's timezone is validated against `pg_timezone_names` by a trigger on `shops`, not by Express and not by a CHECK constraint. | P2-07 made the engine evaluate every wall-clock rule in the shop's own timezone, which turned a previously inert bad value into a total booking outage: the only prior constraint was a length check, so `'Manila/NotAZone'` was storable and now raises inside the gate as a 500. A trigger covers service-role writes, which bypass Express on some paths; a CHECK cannot, because recognising a zone means consulting a catalogue and CHECK expressions must be immutable. The engine deliberately does not re-validate per booking, since `pg_timezone_names` enumerates the whole zone database on every call — one gate at the write boundary is enough precisely because it covers every writer. | Active |
| D-028 | 2026-07-30 | Answers Q20. A provider-enabled owner gets a `barbers` row as a foreign-key anchor only, mirrored one way from `owner_provider_profiles`, rather than repointing `appointments` and thirteen other tables at a new provider identity. | `appointments.barber_id` references `barbers(id)`, so without a row there an owner cannot hold a booking at all — and that was not theoretical: a shop whose only provider is its owner could publish, appear in the catalogue, and refuse every customer, which is a common Philippine barbershop. The duplicate-state objection that D-009 raises is answered by direction rather than by absence: the capability profile stays the only place the value is authored, a trigger mirrors it into the shadow, and nothing writes the shadow. Owners do not leak into barber-shaped reads because the public barber query filters `users.role = 'barber'`. Three pre-existing guards were extended, never weakened — the appointment assignment lock, the `barbers` capability-enablement lock, and the provider predicate — each re-deriving ownership from `shops` rather than trusting the capability row. The full `providers` seam stays available later as a pure refactor with no behavioural change. | Active |
| D-029 | 2026-07-30 | Publication requires at least one provider who is qualified for an active service. | The readiness checklist covered identity, map pin, timezone, chairs, hours, and one active service, but never that anyone could take a booking, so a shop could publish into the catalogue and turn away every customer with no explanation at publish time. Checked at publish only: an owner whose last barber leaves afterwards keeps a published shop with no slots, because unpublishing a shop behind the owner's back is worse than letting them see and fix it. Deliberately ignores the momentary `accepting_bookings` toggle, so a shop cannot be blocked from publishing merely because its barber is on a break today. | Active |
| D-030 | 2026-07-30 | A precondition failure and a stale read get different API error codes: `P4021` maps to `precondition_failed`, `P4020` keeps `conflict`. | The client's correct reaction to the two is opposite — reload and retry versus fix something first — and they shared one code, so no screen could tell them apart. Found in browser smoke: publishing a shop with nobody bookable displayed "the shop changed from another session, we reloaded", telling the owner to reload for a problem no reload can fix. Pre-existing, since closing every operating day and retiring the last active service both behaved the same way; the P2-07 publish guard only made it likely to be hit. No frontend change was needed because Shop Setup's fallback branch already renders the server message. | Active |
| D-031 | 2026-08-01 | The landing page is the hero and nothing else. `#how`, `#services`, `#contact`, and the footer are removed, along with the header nav's Services and Contact Us links and the hero's "Watch the Video" button. | Product owner's call. Every removed anchor had a live link pointing at it, so removing the sections without the links would have left three controls that scroll nowhere. Kept in git history rather than commented out. The consequences are recorded rather than guessed: `LandingPage.tsx` drops 729 lines to 179, `LandingPage.css` drops 3602 to 977, and `RiveScene` plus `public/rive/` (2.0 MB of `rive.wasm` and an 81 KB `.riv`) are now referenced by nothing, which also makes `'wasm-unsafe-eval'` removable from both CSP definitions. Those three are left in place pending a decision, since deleting them is not required by this change. | Active |
| D-032 | 2026-08-01 | Delete Rive entirely (`RiveScene`, `public/rive/`, the `@rive-app/canvas` dependency) and drop `'wasm-unsafe-eval'` from both CSP definitions. Resolves the item D-031 left open. | Rive rendered only inside the landing sections removed by D-031, so nothing referenced it: a self-contained dead island of a component, its stylesheet, a 2.0 MB `rive.wasm`, an 81 KB `.riv`, and a runtime dependency. `'wasm-unsafe-eval'` existed solely to let it compile WebAssembly, and nothing else in the app compiles wasm or evaluates strings as code, so `script-src` returns to a bare `'self'`. This also permanently retires the Chrome DevTools "CSP blocks the use of eval" notice, which was the policy working correctly and must never be answered with `'unsafe-eval'`. Reversible: reinstall the dependency and re-add the token together, never the token alone. Note for whoever changes this next — the dev-server override in `vite.config.ts` rewrites the `script-src` string by exact match, so editing the production directive without editing the override silently drops `'unsafe-inline'` and Vite's inline preamble stops running, which presents as a blank page with no console error. | Active |
| D-018 | 2026-07-29 | The local web dev server must stay on port `5174`. | `vite.config.ts` uses `strictPort` and the API's `WEB_ORIGIN` allowlist trusts only `localhost:5174` and `127.0.0.1:5174`, so any other port fails CORS and every authenticated smoke silently breaks.
